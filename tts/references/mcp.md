# TTS MCP

The MCP wrapper is a thin adapter over the durable TTS CLI and queue. It does
not implement a second synthesizer, player, question store, or pairing system.

## Start the server

Resolve `<skill-dir>` to the directory containing `SKILL.md`.

Stdio is the default:

```bash
<skill-dir>/scripts/tts-mcp
```

For public Streamable HTTP, keep the process on loopback and supply the HTTPS
origin presented by a reverse tunnel:

```bash
<skill-dir>/scripts/tts-mcp \
  --http \
  --host 127.0.0.1 \
  --port 8781 \
  --path /mcp \
  --public-url https://example.ngrok.app
```

The public endpoint is `https://example.ngrok.app/mcp`. `--public-url` enables
OAuth 2.1 authorization with MCP protected-resource discovery, authorization
server metadata, dynamic client registration, PKCE S256, resource indicators,
refresh-token rotation, and token revocation. The approval page requires the
current one-use four-character code generated by `tts-mcp`. Every code expires
exactly five minutes after generation and rotates after ten failed attempts.

```bash
<skill-dir>/scripts/tts-mcp pairing-code
<skill-dir>/scripts/tts-mcp pairing-code --rotate
```

The code is written only to the private local TTS state and server stderr. It is
never returned by an HTTP route. The approval page identifies the registered
client and callback host before accepting it. Access tokens last one hour;
refresh tokens rotate and last up to 30 days.

OAuth discovery is available at both
`/.well-known/oauth-protected-resource` and the path-specific
`/.well-known/oauth-protected-resource/mcp`. Authorization server metadata is
at `/.well-known/oauth-authorization-server`. An unauthenticated MCP request
returns `401` with a `WWW-Authenticate` challenge pointing at the path-specific
resource metadata.

Without `--public-url`, HTTP retains static-bearer compatibility for local use:

```bash
export TTS_MCP_TOKEN="<at-least-24-random-characters>"
<skill-dir>/scripts/tts-mcp --http
```

HTTP mode always rejects non-loopback binds and validates Host and Origin
headers. It exposes only a minimal unauthenticated `GET /healthz` probe. Pass
the external origin through `--public-url`; do not bind the process directly to
a public interface.

## ngrok

When an ngrok agent is already running, add a non-disruptive tunnel through its
local Agent API and use the returned `public_url` as `--public-url`:

```bash
curl -X POST http://127.0.0.1:4040/api/tunnels \
  -H 'Content-Type: application/json' \
  -d '{"name":"tts-mcp","proto":"http","addr":"http://127.0.0.1:8781","inspect":true}'
```

The tunnel can start before TTS MCP; requests will succeed after the loopback
server starts with the returned origin. A dynamically created ngrok URL lasts
for the life of that agent tunnel. Use a reserved ngrok domain or managed
service configuration when a durable URL is required.

Use `--allow-origin` for an additional trusted browser origin. Use repeatable
`--allow-root` arguments when local MCP callers need to attach server-local
files. Attachment paths outside those roots and all symlink escapes are
rejected.

## Route ownership

The `--route` option controls where synthesis happens:

- `automatic`: ordinary speech follows the root TTS local-or-paired selection.
  Generation uses an approved pair when present and otherwise runs locally.
- `paired`: speech, questions, and generation are explicitly sent through the
  approved signed pairing to the computer that runs TTS.
- `local`: synthesis is forced onto the MCP host.

For an MCP server deployed on an agent environment paired to a TTS computer:

```bash
<skill-dir>/scripts/tts-mcp \
  --http \
  --public-url https://example.ngrok.app \
  --route paired
```

Keep the paired computer's `tts daemon` listener running. The MCP endpoint stays
on the agent environment; tool requests cross the existing Nostr pairing and
are materialized by the paired computer. The caller never receives a laptop
filesystem path.

Host-local attachments are intentionally rejected in explicit paired mode.
They are not silently published or copied to another computer.

Queue inspection and lifecycle tools operate on the state directory visible to
the MCP process. Spoken asks still return their paired answers directly through
the signed reply path.

## Tools

The three creation tools require `agent_name`, a concise `subject` title, a
one-line non-spoken `summary`, and the spoken `message`. Titles aim for 2-5
words and must not exceed 10 words.

- `tts_speak`: generate and queue an audible update.
- `tts_ask`: present one to three structured questions and wait for a bounded
  answer.
- `tts_generate`: generate without playback, upload the MP3 to Blossom, and
  return only the hosted descriptor.
- `tts_status` and `tts_health`: inspect playback and route health.
- `tts_list_items` and `tts_get_item`: read bounded durable queue views.
- `tts_wait_for_item`: wait for an answer or terminal playback state.
- `tts_http_header_traffic`: read a bounded recent view of inbound HTTP headers
  and response statuses with sensitive values redacted.
- `tts_archive_items`, `tts_restore_items`, and
  `tts_supersede_questions`: apply audited lifecycle operations.

Persistent playback behavior remains owned by the TTS app Preferences rather
than MCP tools.

## Hosted generation

`tts_generate` is the MCP equivalent of `tts --no-play`, with an external result
contract:

1. It never queues playback.
2. In paired mode, the paired computer performs synthesis and upload.
3. The MP3 is uploaded with Blossom `PUT /upload` to
   `https://blossom.primal.net` by default.
4. The upload uses a short-lived Nostr kind `24242` authorization event scoped
   to the server hostname and exact MP3 SHA-256.
5. The result contains `status`, `url`, `sha256`, `size`, `type`, `uploaded`,
   and `server`; it never contains `output_file`.

Example structured result:

```json
{
  "status": "uploaded",
  "url": "https://blossom.primal.net/<sha256>.mp3",
  "sha256": "<sha256>",
  "size": 12345,
  "type": "audio/mpeg",
  "uploaded": 1784260000,
  "server": "https://blossom.primal.net"
}
```

The paired request and reply are readable signed kind `9` events. The reply
uses native tags for the URL, hash, size, MIME type, upload time, and server; it
does not hide the result in a JSON tag.

## Header traffic and privacy

Every inbound HTTP request is recorded after completion, including OAuth
discovery, rejected authorization attempts, and authenticated MCP traffic. The
JSONL log defaults to:

```text
~/.local/state/tts/mcp/http-headers.jsonl
```

Inspect it through the authenticated `tts_http_header_traffic` tool or locally:

```bash
<skill-dir>/scripts/tts-mcp headers --limit 100
tail -f ~/.local/state/tts/mcp/http-headers.jsonl
```

Entries include timestamp, duration, method, path, response status, client
address, query parameter names, and inbound headers. Query values are omitted.
Authorization, cookies, API keys, client certificates, and any header whose
name contains `token`, `secret`, `cookie`, or `key` are replaced with a short
one-way fingerprint. The active file rotates at 2 MiB.

## Resources and privacy

The server exposes `tts://status`, `tts://health`, item records, generated audio,
and item attachments as MCP resources. Item views replace filesystem paths with
resource URIs and remove workspace paths, commands, terminal identifiers, and
answer attachment paths.

MCP request and header logs do not include message, answer, form, or query
values. HTTP mode requires OAuth or a local static bearer because TTS tools can
create public audio and cause audible playback.
